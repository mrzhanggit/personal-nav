    • 1为什么需要版本控制：你的项目需要存档系统

    每个写过代码的人都经历过这个惨案文件夹：

    毕业设计/ ├── 报告.docx ├── 报告_最终版.docx ├── 报告_最终版2.docx ├── 报告_真最终版.docx └── 报告_真最终版_打死不改.docx # ……然后导师说：还是第 2 版好

    更惨的是：改崩了没法撤销、删错了没法找回、两台电脑来回拷贝覆盖。Git 就是代码界的游戏存档系统——它把项目的每一次改动都拍成快照存起来，你随时可以读档。

    git checkout
    回档
    打崩了？读任意一次旧存档
    git branch
    多剧情线
    开新支线，翻车不伤主线
    commit -m
    存档说明
    每档写清楚存了什么
    push / pull
    云存档
    换电脑不丢档，队友共享

    从今天起，你写的不只是「脚本」，而是有历史、有档案、可回溯的工程项目。这也是公会对高阶玩家的硬性要求。

    2三板斧与三区模型：存档的正确姿势

    把一个普通文件夹变成 Git 仓库、完成第一次存档，只需要三条命令：

    $ git init # ① 开机：把当前文件夹升级成 Git 仓库 Initialized empty Git repository in /Users/hero/quest/.git/ $ git add quest.py # ② 打包：把 quest.py 的改动放入暂存区（成功时无输出） $ git commit -m "feat: 角色名片第一版" # ③ 存档：把暂存区快照永久写入仓库 [main (root-commit) a1b2c3d] feat: 角色名片第一版 1 file changed, 2 insertions(+) create mode 100644 quest.py

    理解 Git 的钥匙是这张三区模型图——你的文件改动像闯关一样，要穿过三个区域：

    🖥 工作区 Working Dir

    你正在编辑的文件
    最新改动，还没打包
    git add
    ────➤

    📦 暂存区 Staging

    打包好的待存档清单
    决定「这一档存什么」
    git commit
    ────➤

    🗄 仓库 .git

    带哈希的永久快照
    a1b2c3d ← 第一档

    为什么要多一个「暂存区」，不直接存档？因为存档前你常常想挑着存：这一关你打了 3 个怪、捡了 2 件装备，可以只存「捡装备」这件事。add 负责挑，commit 负责存——分工明确。

    继续修改、继续存档，历史就一档一档摞起来了：

    # ……给 quest.py 又加了两行代码，然后： $ git add quest.py $ git commit -m "feat: 增加金币系统" [main 7d2e4b9] feat: 增加金币系统 1 file changed, 2 insertions(+)

    3时间旅行：git log / diff / checkout

    查看存档历史——每个快照都有一个 7 位短哈希当「存档编号」：

    $ git log --oneline
    7d2e4b9 (HEAD -> main) feat: 增加金币系统 a1b2c3d feat: 角色名片第一版

    最新的在最上面，HEAD 指向当前所在的存档。想知道这次到底改了什么？

    $ git diff # 查看工作区里还没提交的改动
    diff --git a/quest.py b/quest.py index 83db23f..4a2c9e1 100644 --- a/quest.py +++ b/quest.py @@ -1,2 +1,3 @@ hero = "阿呆" print("你好，" + hero) +gold = 300

    + 开头的行是新增，- 开头是删除——diff 就是改动的「对账单」。

    最刺激的来了：读档回退。把 quest.py 恢复到第一版：

    $ git checkout a1b2c3d -- quest.py # 命令本身没有任何输出，但 quest.py 已悄悄变回第一版

    ⚠️ 回档风险须知：checkout 会用旧版本覆盖工作区——你手头还没 commit 的新改动会被直接冲掉，且基本找不回来。读档之前，先存档。想再回到最新版，读 main 线的最新存档即可：git checkout main -- quest.py。

    4剧情线、云存档与公会规范

    ① 分支：多开剧情线。主线 main 是稳定通关版；想试新功能，开一条支线随便浪，翻车了主线毫发无伤：

    $ git branch dev # 创建剧情线 dev $ git switch dev # 切换到 dev 上开发 Switched to branch 'dev' # ……在 dev 上改代码、add、commit…… $ git switch main # 试炼结束回主线 Switched to branch 'main' $ git merge dev # 把 dev 的剧情并入主线 Updating a1b2c3d..7d2e4b9 Fast-forward quest.py | 3 ++- 1 file changed, 2 insertions(+), 1 deletion(-)

    ② 远程仓库：云存档。GitHub / Gitee 就是你的云存档服务器。push 上传、pull 下载：

    $ git push -u origin main # 上传：本地存档 → 云端 Enumerating objects: 6, done. Counting objects: 100% (6/6), done. Writing objects: 100% (6/6), 1.02 KiB | 1.02 MiB/s, done. Total 6 (delta 0), reused 0 (delta 0), pack-reused 0 To github.com:hero/quest.git * [new branch] main -> main branch 'main' set up to track remote branch 'main' from 'origin'. $ git pull # 下载：把云端最新进度拉回本地 Already up to date.

    ③ .gitignore：不是所有东西都配进存档。可重建的、体积巨大的、以及会害死你的秘钥，都要拉黑：

    # .gitignore —— Git 的忽略清单 __pycache__/ # Python 运行缓存，每台机器自己会生成 venv/ # 虚拟环境，几百 MB 且一条命令就能重建 .env # 秘钥文件！API key 一旦推上 GitHub 全网可见，立刻作废 *.pyc # 所有编译产物

    🚨 血泪规矩：.env 必须在第一次 add 之前就写进 .gitignore。秘钥一旦推上公开仓库，唯一正确操作是立刻去平台后台作废重发。

    ④ 标准项目结构：一个像样的 Python 项目长这样。（明天毕业设计就照这个骨架搭）：

    my_assistant/ ├── README.md # 说明书：干什么的、怎么安装、怎么运行 ├── main.py # 主程序入口，只负责调度 ├── config.py # 配置集中营：路径、开关、常量 ├── modules/ # 功能模块：一个职责一个文件 │ ├── organizer.py │ └── reporter.py ├── tests/ # 测试代码，与模块一一对应 │ └── test_organizer.py ├── requirements.txt # 依赖清单：pip install -r requirements.txt 一键装齐 └── .gitignore # 忽略清单（见上）

    ⑤ 写测试的意识。项目越大，越不敢「改一行跑全篇」。用 pytest 给核心函数上保险：

    # tests/test_add.py def add(a, b): return a + b def test_add(): assert add(1, 2) == 3 # 断言：add(1,2) 必须等于 3 assert add(-1, 1) == 0
    $ pytest
    ================= test session starts ================= platform darwin -- Python 3.12.0, pytest-8.2.0, pluggy-1.5.0 rootdir: /Users/hero/my_assistant collected 1 item tests/test_add.py . [100%] ================== 1 passed in 0.01s ==================

    pytest 会自动发现所有 test_ 开头的函数并运行，通过一个绿点、失败一片红——改完代码跑一遍，心里有底。

    ⑥ commit message：写给未来的自己的短信。半年后翻 log，全靠它认出每档存了什么：

    ✅ feat: 增加金币掉落系统 # 类型 + 干了什么，一目了然 ✅ fix: 修复背包溢出时的崩溃 ❌ 改了点东西 # 等于没写 ❌ final_final_v2_真的最终版 # 这是文件名的惨案，别让它复活

    常用类型：feat 新功能、fix 修 bug、docs 改文档、refactor 重构。一行说清，动词开头。

    5🎮 实验室 · Git 时光机

    三区模型光看不练等于没学。这台「时光机」里有一个 quest.py：点 编辑 改代码，git add 打包进暂存区，git commit 生成带哈希的存档。存两档以上后，点「回到第一次提交」亲眼看 checkout 读档。下方终端同步打印每一步真实的 git 命令与输出。

    ⚠️ 读档完成。注意：如果你刚才在工作区有还没 commit的新改动，它们已经被旧版本覆盖——这就是 checkout 的代价。重要的新改动，永远先 commit 再回档。

    🖥 工作区 quest.py

    git add
    ────➤

    📦 暂存区 index

    git commit
    ────➤

    🗄 仓库 .git

    隐藏玩法：先「编辑」再直接「git commit」（跳过 add），看看真实 Git 会怎么吐槽你。也可以 checkout 回第一档后再 add + commit，把「回档版」存成新一档。
